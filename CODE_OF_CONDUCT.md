# Code of conduct

## The short version

Be decent. Assume the other person is competent and acting in good faith. Argue
about the code, not the person writing it.

## What is expected

- **Criticise work, not people.** "This allows a suffix-confusion bypass" is
  useful. "This is amateur work" is not, and says nothing a maintainer can act on.
- **Assume competence.** People come to this project from different backgrounds —
  virtualisation, networking, security research, or just wanting their agent to
  stop touching things. Someone unfamiliar with one area is usually expert in
  another.
- **Be direct and be kind.** These are compatible. Security review requires blunt
  findings; it does not require contempt.
- **Accept that maintainers will say no.** This is a deliberately small tool
  (see CONTRIBUTING.md). A declined feature is a scope judgement, not a verdict
  on you or your idea.
- **Respect disclosure.** If you find something exploitable, follow
  [SECURITY.md](SECURITY.md) rather than posting it publicly. This protects
  people running the tool, not the maintainers' reputation.

## What is not acceptable

- Harassment, insults, or personal attacks, in issues, pull requests or any
  other project space.
- Demeaning comments about someone's identity — including but not limited to
  age, disability, ethnicity, gender identity or expression, nationality,
  personal appearance, race, religion, or sexual orientation.
- Sustained disruption: repeatedly reopening settled decisions, brigading a
  thread, or demanding unpaid work from volunteers.
- Publishing others' private information without permission.
- Weaponising the security process — filing reports in bad faith, or using a
  disclosure timeline as leverage.

## Scope

This applies in every project space: issues, pull requests, discussions, commit
messages, and any venue where someone is representing the project.

## Reporting and enforcement

Report a problem by opening a private GitHub security advisory on the repository
(**Security → Report a vulnerability** — it works for conduct reports too and is
not publicly visible), or by opening an issue asking a maintainer to make
contact, with no details in it.

Reports are handled privately. Maintainers will acknowledge within about a week
and say what they intend to do. Responses escalate with severity and repetition:

1. A private word explaining what was wrong.
2. A public correction in the thread.
3. A temporary ban from project spaces.
4. A permanent ban.

Maintainers who violate this document should be held to it more strictly than
anyone else, not less. If the person you need to report is a maintainer, say so
in the report and it will be handled by someone else where that is possible.

## A note on the subject matter

This project attracts adversarial thinking by design — the whole point is that
people try to break it. Finding a hole and saying so plainly is exactly the
contribution we want, and no amount of bluntness about a *vulnerability* is a
conduct problem. The line is between the work and the person.
